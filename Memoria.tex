\chapter{Estado del arte en el ámbito tecnológico}

Para implementar este tipo de sistemas requerimos de tecnologías que nos permitan implementar las funcionalidades que deseamos mediante: 

\begin{enumerate}
    \item Un servidor que hace el papel de API que se conecta a: una base de datos para persistir datos tabulares y relacionales y un almacenamiento de objetos para guardar imágenes de perfil y documentos.
    \item Una interfaz multiplataforma que se conecta a la API para mostrar los datos persistidos e interactuar con ellos.
\end{enumerate}

Para implementar la API podemos elegir entre varios lenguajes de programación y sus correspondientes frameworks y librerías: Python con FastAPI o Django, PHP con Laravel, Rust con Tokio y Java/Kotlin con SpringBoot entre otros. 

Para la \ac{BD} encontramos opciones como MySQL, PostgreSQL, SQL Server, Oracle, MariaDB si queremos un sistema relacional. Aunque también podemos optar por MongoDB, Redis o Cassandra, entre otros, si preferimos sistemas no relacionales.

Para el \ac{OS} la opción más utilizada es el almacenamiento en la nube que ofrece Amazon S3. Una alternativa a Amazon S3 podría ser Cloudflare R2. Estas soluciones alojadas en la nube acarrean un costo si el volumen de datos y consultas es alto. Lo bueno es que podemos optar por versiones autoalojadas para tener más privacidad y control sobre los recursos, además de eliminar cualquier costo. La última opción, pero menos recomendada, sería guardar las imágenes y documentos en una carpeta del sistema de ficheros del servidor donde se aloja el back-end. 

Finalmente, para implementar la interfaz de usuario gráfica multiplataforma podemos optar por las siguientes tecnologías: React Native, Ionic y Quasar, basadas en tecnologías web; o Flutter y Kotlin Multiplataforma, basadas en tecnologías nativas.


\section{Tecnologías utilizadas}

Entre todas estas tecnologías se han seleccionado las más convenientes y útiles dados ciertos criterios, algunos de ellos objetivos, pero otros completamente subjetivos.

La interfaz gráfica está implementada utilizando React Native. La razón principal de esta elección se debe a que ya he tenido experiencia desarrollando páginas web con React. Esto hace que no sea necesario aprender nuevos lenguajes, sino que simplemente puedo aplicar el conocimiento que ya tengo junto a una tecnología que aporta el desarrollo multiplataforma de forma nativa. Así mismo, he utilizado el empaquetador de Expo, altamente recomendado en la propia documentación de React Native. De esta forma, el desarrollo es mucho más cómodo, y es posible compilar el código a cualquier plataforma sin problemas.

El servidor back-end se ha implementado en Spring Boot-Kotlin. La elección de Kotlin se debe a: la baja curva de aprendizaje por haber tenido experiencia con otro lenguaje basado en la JVM, como es Java; y en la practicidad y facilidad de programación y entendimiento que ofrece Kotlin como herramienta de codificación. Se ha elegido Spring Boot porque aporta sencillez a la hora de crear aplicaciones que escuchan y sirven peticiones. Es capaz de soportar una alta carga de usuarios concurrentes manteniendo simplicidad en el código.

La \ac{BD} ha sido implementada utilizando el motor de PostgreSQL. Podría entenderse que la mejor opción era MySQL o MariaDB, ya que son las tecnologías que se enseñan dentro del \ac{GEIN}. Dichas opciones se tuvieron en cuenta, pero a decisión personal, finalmente se optó por PostgreSQL debido a un interés en aprender a utilizar esta tecnología. Según Stack Overflow es el motor más popular dentro del mundo del desarrollo abarcando más de la mitad de la cuota de mercado \href{https://survey.stackoverflow.co/2025/technology#1-databases}{Stack Overflow Survey}. Esto la convierte en una tecnología que vale la pena investigar y aprender a usar.

Finalmente, para el \ac{OS} se ha decidido utilizar un contenedor de Docker de MinIO que se ejecuta localmente en el servidor junto al back-end. Las razones principales han sido la privacidad, el control y el nulo coste de uso de la herramienta para el caso que nos acontece. MinIO permite tener un \ac{OS} con control total de los recursos sin necesidad de optar por el almacenamiento en la nube. Además, la API utilizada en Spring Boot es completamente compatible con la de Amazon S3, por lo que si en algún momento fuera necesario escalar el almacenamiento y llevarlo a la nube, tan solo haría faltar cambiar algunas variables de entorno.
